# Project Development Blueprint

`project-development-blueprint` 用于把业务需求和现有代码库整理成可以直接交给开发者或 AI 编码工具执行的项目开发蓝图。

它关注的不只是“要做什么”，还会说明：

- 业务目标如何拆成角色、场景、规则和验收标准；
- 当前代码和目标架构之间的差距；
- 模块、接口、数据模型和配置的职责边界；
- 每个技术选择为什么适合当前项目；
- 具体修改哪些文件，以及如何测试和发布；
- 哪些需求、假设和风险仍需要确认。

## 适用场景

- 新项目的架构设计；
- 现有项目的功能扩展或重构；
- 需要交给另一位开发者或 AI 编码工具实施的复杂需求；
- 需要同时梳理产品、业务流程、技术方案和验收标准的企业项目；
- AI 功能、文件处理、外部 API、权限、数据迁移等容易产生设计遗漏的工作。

不适用于只需要解释一段代码、执行小型机械修改，或已经有明确实施方案的简单编码任务。

## 使用方式

直接描述项目目标和背景即可，例如：

```text
使用 project-development-blueprint，为现有订单系统设计退款功能。
请先分析代码库，再生成可交给 AI 编码工具执行的实施蓝图。
```

如果希望在设计过程中学习业务拆解和架构设计，可以开启教学模式：

```text
使用 project-development-blueprint，并开启教学模式。
每个关键业务拆解、架构决策和代码设计都解释为什么这样做。
```

教学模式会对重要决策补充以下内容：

1. 业务目标如何转化为工程需求；
2. 选择了什么设计；
3. 为什么选择它，以及放弃了哪些替代方案；
4. 设计最终落在哪些文件、接口、函数、表或测试；
5. 如何验证实现符合预期。

它只解释会影响行为、维护性、安全、成本或运维的关键决策，不会把每个字段都展开成教程。

## 输出内容

根据项目规模，skill 会选择一种输出形式：

- 小型项目：一份完整 Markdown 蓝图；
- 中大型项目：一个包含索引、需求、现状、架构、契约、实施计划和验证发布文档的目录。

蓝图通常包含：

- 项目目标、范围、参与角色和场景；
- 当前架构与目标架构；
- 技术选型及替代方案；
- 模块契约、API、数据模型和迁移策略；
- 权限、隐私、错误处理、重试、幂等和并发行为；
- 配置、日志、指标、部署、回滚和验收标准；
- 有序实施任务和分阶段 AI 编码提示；
- 验证矩阵、剩余不确定性和最终结论。

## 设计原则

- 先确认业务结果，再决定技术方案；
- 区分已验证事实、推断和未知信息；
- 每个重要新增模块都必须有真实消费者和可验证作用；
- 采用满足当前规模和风险的最小充分架构；
- 不凭空添加业务规则、合规要求、SLA、费用或数据保留期限；
- AI 功能必须有真实的运行时 provider 路径，不能把假数据当成生产行为；
- 蓝图只产生文档，不直接修改业务代码、执行迁移、部署或提交代码。

## 目录结构

```text
project-development-blueprint/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── references/
    ├── guided-design-and-execution.md
    ├── small-project-template.md
    └── large-project-template.md
```

`SKILL.md` 是运行规则；`references/` 存放按项目规模和场景读取的模板与详细流程；本 README 面向使用者，不作为生成蓝图的模板。

## 结果判定

每份蓝图都会给出以下结论之一：

- `IMPLEMENTABLE`：信息和设计足够，可以开始实施；
- `REDUCE_SCOPE`：需要缩小第一阶段范围；
- `REVISE_DESIGN`：当前设计存在矛盾或明显风险；
- `NEEDS_EVIDENCE`：需要补充代码、运行或业务证据；
- `NO_CHANGE_NEEDED`：现有能力已满足目标。
